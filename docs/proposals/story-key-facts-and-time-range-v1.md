## 一句话

Story（一件事）的「当前认识」从 2 项变成 4 项——标题、摘要、**这件事发生在什么时候**、**几条关键事实**；并且改这四样都会留下历史版本。

## 为什么需要它（用信息库里的实际情况举例）

三个来源都在说同一件事，你把它们归到了同一个 Story：

```text
官方公告   9/14 发布
门户转载   9/16
测评视频   9/17
```

**问题 1：没有地方写「这件事什么时候发生的」。**

界面上现在只有一个时间线，它只能按每条内容**自己的发布时间**排：9/14 → 9/16 → 9/17。于是：

- 想知道「这事发生在什么时候」，只能自己从时间线猜；而 9/16 其实什么都没发生，只是有人转载；
- 如果事件 9/14 发生、报道 9/22 才出来，时间线会显示 9/22，把「事后复盘」误导成「事件发生日」；
- 只知道「2026 年某时」时，没有「精确到什么程度」的概念，存进去就得假装是某一天（比如 1 月 1 日），显示和排序都会撒谎。

**问题 2：没有地方写「关键事实」。**

你读完三条内容，得出三条结论：「上下文 1M」「9/14 发布，对标 GPT-5」「第三方测评说长文本仍会衰减」。现在这三条只能：

- 塞进**摘要**——但那是一段叙述，不能单独引用、不能排序，也没法标注「这条是从哪条内容看出来的」；
- 或者写成**批注**——但批注是「你个人的笔记」，不是「这个 Story 的当前认识」，将来 Agent 分不清哪条是事实、哪条是观点。

**问题 3：就算硬加两个字段，也留不下历史。**

Story 的价值之一是「改过什么、什么时候改的」能追溯。真实会发生的情况：9/14 你写「上下文 1M」，9/18 官方更正说「1M 是传闻，实际 512K」——

- 如果只是覆盖写，9/14 的判断就永久消失；
- 更麻烦的是：将来 Agent 基于 9/14 的记录生成过一份报告，官方一更正，那份报告里的数字会被「追着改」，而报告当时确实是按 1M 写的。

所以这两项必须跟标题/摘要一样走**版本**：改了产生新版本，旧版本只读保留。

## 目标

1. Story 能表达**事件发生的时间范围**，并且保留「精确到什么程度」和「依据是什么」。
2. Story 能保存**一组有序的关键事实**，每条可以挂一条出处（这条事实是从哪条内容看出来的）。
3. 两项都走既有的版本机制：改了产生新版本，内容没变时不产生新版本；**升级后老数据的行为不能变**。
4. 界面上能填能看；拆分 Story 时每个新 Story 各自带自己的这两项。

## 非目标

- ADR-0006 决定 3 提到的第三项「结构化概览」仍留在后续切片。
- 自动抽取事实、LLM 总结（ORG-021 / Knowledge Workflow）。
- 跨 Story 的时间对齐、事件时间推断、时间线可视化重做（现有时间线行为不变）。
- Story 之间的先后/背景关系（信息模型 §4.5 的 `followed_by`/`background_for`）。
- 时间范围的提醒、过期、日历视图。
- Phase 1 后置债：Docker/Compose、发布部署、真实公网长时定时、非 Windows smoke、长时故障恢复。

## 方案（大白话）

### 1. 时间范围支持三种填法

| 你知道多少 | 怎么填 | 系统怎么处理 |
| --- | --- | --- |
| 准确时间 | 「2026-09-14 09:30」 | 精确到分钟，可按时间排序 |
| 只到某天 | 「2026-09-14」 | 精确到天，显示「9 月 14 日」 |
| 只到某年 | 「2026 年」 | **按年显示和排序，不会假装是 1 月 1 日** |
| 只有原文 | 「昨天下午」 | 保留原文，标记为不精确 |
| 起止都知 | 「9/14 – 9/16」 | 事件时间范围 |

只有开始时间表示「起点已知」；两个都不填表示未定；结束时间早于开始时间会被拒绝。**所有类型的 Story 都能填、也都能不填**（一次发布动作本身就是一个时间点，按类型硬性禁止会挡住合理用法）。

### 2. 关键事实是一个有序清单，每条挂一条出处

```text
1. 上下文窗口 1M                 ← 出处：官方公告
2. 9/14 发布，对标 GPT-5          ← 出处：官方公告
3. 第三方测评认为长文本仍会衰减    ← 出处：测评视频
```

- 顺序就是你排的顺序（不另设「重要度」字段，避免两套顺序）。
- 出处只是**一个指向**：点它跳过去自己核对。它**不要求**属于这个 Story——因为一条内容只能有一个主归属，如果要求「出处必须是本 Story 的成员」，那么用另一篇（比如一份行业周报里顺带提到的日期）作依据就永远写不进来；而且成员被移走时，要么系统自动删掉你写的事实，要么留下一个指不回去的出处，两个都不好。
- 界面上默认优先列出本 Story 的条目，找不到再让你搜全局。
- v1 **只由你手动填**，不自动生成。

### 3. 改动留下版本

把时间从「9/14」改成「9/14–16」、把「上下文 1M」改成「512K」，都产生新版本；旧版本里当时写的内容仍然查得到。内容完全没变时不产生新版本。

### 4. 界面上

- 详情页标题下面显示事件时间（按精度显示，如「2026 年 9 月 14–16 日」），关键事实单独一块；
- 编辑表单能填时间范围、增删改和排序事实、给每条选出处；
- 组件实验室登记对应场景。

### 5. 拆分 Story 时

拆分产生的每个新 Story 各自填自己的时间范围和事实（**不**自动把原 Story 的复制过去）。这和现在拆分要各自填标题/摘要的规则一致。

## 已裁定的决定

| # | 决定 | 说明 |
| --- | --- | --- |
| 1 | 时间范围复用既有的时间语义（起止 + 精度 + 依据） | 不新造时间概念，和 Entry 侧口径一致 |
| 2 | 关键事实 = 有序文本 + 可选出处（每条一条） | 不做结构化键值对 |
| 3 | 两项都参与变化判定 | 变了才产生新版本 |
| 4 | 兼容策略：**两项为空时，判定结果与升级前逐字节一致**，不做全库回填 | 避免升级后没改东西也凭空多出版本 |
| 5 | 写入沿用「全量提交当前表示」（省略即清空） | 保持单一写入语义；代价见下 |
| 6 | 拆分后继同批支持，不迁移原值 | — |
| 7 | 时间范围不按 kind 限制，允许留空 | 2026-09-16 裁定 |
| 8 | 不做「已确认 / 推测」标记 | 等 ORG-021 有自动生成的事实写入者再评估 |

**决定 5 的代价（需要你知道）**：表单提交的是「一份完整的当前认识」，所以**没带上的字段 = 清空**。将来任何别的入口（尤其是 Phase 3 的 Agent 写候选版本）都必须把这两项原样带上，否则会清空。备选方案是「没提到就不动」，代价是同一件事出现两种提交方式。已按保持现状裁定，并写进 ADR-0021 的 Revisit Gate，等 Phase 3 验证。

## 实现细节（附录，给实现者）

### 字段形状与校验

- `timeRange: { start: TemporalValue; end: TemporalValue | null } | null`，复用 domain 的 `TemporalValue`（`exact`/`exactPrecision`/`fallback`）；`end < start` 拒绝。
- `keyFacts: { text: string; entryId: string | null }[]`：最多 20 条，`text` 最长 500 字；`entryId` 必须存在（不存在按现有错误映射返回 404/400）；读取时对已删除条目降级为「无出处」。
- 持久化形状（ISO 字符串 + 精度 + 原始文本、事实的 JSON 文本列或子表）由实现设计阶段冻结，migration forward-only、既有行为空。

### 变化判定与升级兼容

`fingerprintStoryRevision` 目前是 `JSON.stringify({title, summary, kind, subtype})` 的 SHA-256（`packages/domain/src/index.ts:383-390`），`packages/storage-prisma/src/repository/stories.ts:103-111` 用「当前 Revision 的 fingerprint 是否等于新算指纹」判定 no-op。加入两项后必须保证：**两项为空时序列化结果与升级前逐字节相同**。回归断言用「升级前固定输入对应的期望指纹」钉死，并覆盖「设值 → 清空 → 再提交回到 no-op」。

### 写入与读取

- 扩展 `POST /api/v1/stories/:storyId/revisions`（`updateStoryRevisionCommandSchema`）：两项可选、省略即清空；`storySplitSuccessorSchema` 同步增加同名字段。
- `StoryDetail` 增加两项（向后兼容新增）；Story 的时间线读取行为不变。

### 受影响合同与预计核心文件

- contracts（`packages/contracts/src/story.ts`）、domain（`packages/domain/src/index.ts`：`StoryRevisionContent` 与指纹）、storage（`schema.prisma` + migration、`repository/stories.ts` 写入与读取）、api（`apps/api/src/app.controller/content.ts`）、transport（`packages/transport-http/src/client-content.ts`）、web（`apps/web/src/components/cosmos/story-panel.tsx`、`apps/web/src/app/home/use-story-workspace.ts`）。
- 横跨全链，约 8 个核心实现文件，按「域 + 持久化 → 合同 + API → Web」三步走，每步可独立合入。

### 验证层级（验收草案）

- **focused（domain/contracts/storage）**：新字段参与判定导致实质变化；**空扩展字段时指纹与升级前逐字节相同**；`end < start`、超限、出处不存在被拒绝；新增/修改/清空各产生一次新版本；相同内容重复提交不产生新版本；**升级后的既有 Story 不改任何字段时仍是 no-op**；split 后继带这两项。
- **API 集成**：命令校验与错误映射、`StoryDetail` 读取投影。
- **浏览器**：给多来源 Story 填时间范围与两条事实 → 详情按精度显示、事实顺序保持；重复提交相同内容后版本不增加；拆分成两个后继时各自带自己的时间范围。
- **隔离库 upgrade 两态**：含旧数据的库升级后行为不变。
