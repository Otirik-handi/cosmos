# 已知不稳定的测试用例

本文件登记**已观察到、但尚未修掉**的测试不稳定（flaky）用例：症状、实际观察到的证据、当前判断（含不确定的部分）和建议的处理次序。它是排查入口，不是当前验证结论——哪一层已通过或未运行，以 [`PROJECT-STATUS.md`](../../PROJECT-STATUS.md) 为准；测试分层与命令见 [`README.md`](README.md)。

登记规则：

- 只记「同一条用例在没改代码的情况下既过又挂」的情况；确定性失败是缺陷，按 Bug 处理，不进本表。
- 证据必须写明**实际跑过的命令、次数与每次结果**，不能只写「偶发」。
- 不确定的地方要写出来。把「不知道」写成「无害抖动」是本文件最想避免的事。
- 修掉之后从表中移除，并把结论写进对应的 Task 或 `PROJECT-STATUS.md`。

## 1. `e2e/browser/phase2-organization.spec.ts` 的间歇失败

**状态（2026-09-17 更新，含一次更正）**：`:539` FTS5 搜索用例已查明并修复，但**根因不是陈旧响应竞态**（早先的归因有误，下面第 32 行的观察结论已按证据更正）。真实根因是 Feed 卡片列表的 **React key 重复**：同一 Story 可以有多张成员卡片同时出现在 Feed 里（ADR-0022 决定 4/6「只标记、不折叠」），列表却用 `storyId` 当 key，React 只接管其中一张，另一张的 DOM 节点不再受它管理——列表被整体替换后它就留在原地成为「幽灵卡片」，而此时提示语与 React 状态都已经是 0 条。修复（`key` 改用条目身份 `entryId`）与**确定性**回归用例（同一 spec 修复前必挂、修复后 14.9 秒通过）见 Task [`30`](../../.agents/tasks/30-feed-stale-response-race/README.md)。同一次排查顺带确认了另一个**真实竞态**（搜索之后才返回的陈旧刷新会覆盖搜索置空的列表），已同批修复并带独立回归用例，但它不是 `:539` 的成因。本条现在只覆盖**仍未归因的 `:103`（证据关系反向视图等待超时）与 `:417`（用户组织场景耗时异常，单次 5.1 分钟）**。

**症状**：整个 spec 文件连跑时，某个用例失败；失败点会在用例之间**漂移**，单跑又通过。

**实际观察（2026-09-15）**：

| 跑法 | 结果 |
|---|---|
| 合并看板切片后在 `master` 跑整套浏览器套件 | 17/18，失败的是「拆分场景」 |
| 单跑该拆分用例 | **5/5 通过** |
| 整个 spec 文件连跑 3 次 | 1 次 6/6；1 次失败的是**另一个**用例（证据关系场景 `toBeVisible` 超时）；1 次 6/6 |
| 搜索修复切片（2026-09-15）整套 + 该文件多次连跑 | 19/19；该文件连跑均通过，**未复现** |
| 2026-09-17 分支 run（`workflow_dispatch`，与 master 内容 diff 0 行） | 该文件全通过，但 `spec.ts:103`「证据关系反向视图」判为 **1 flaky**（失败后重试通过）；另一次 master run 35179029322 该文件全通过 |
| 2026-09-17 Task 26 worktree：整套连跑 4 次（含新增的`phase2-entry-relation.spec.ts`） | 4/4 都有失败：3 次是 `:539` FTS5 搜索用例的 `toHaveCount`（见下），1 次是 `:103` + `:539` |
| 2026-09-17 Task 26 worktree：整套连跑 4 次（移走该新 spec，其余不变） | 3 次 21/21 通过；1 次失败在 `media-policy.spec.ts:89`（耗时 5.1 分钟，像是卡死而非断言失败） |
| 2026-09-17 Task 26 worktree：整套跑，额外加一个**只做既有行为**的诊断 spec（录入一个来源 + 归并两条 Story，完全不碰新功能） | 20/22，失败在 `:103` 与 `:417`（后者耗时 5.1 分钟） |
| 2026-09-17 Task 26 worktree：整套跑，额外加一个只录入来源、不归并的诊断 spec | 22/22 通过 |
| 2026-09-18 Task 31 worktree：同一 build 整套连跑 2 次（`bun run test:browser`） | 第 1 轮 **22/22 通过**；第 2 轮 **21/22**，失败在 `:186`「拆分场景」，同 build 单跑该用例 **1 passed (3.2s)** |

**2026-09-17 关于 `:539` 的补充观察（Task 26 期间）**：失败现场 `role=status` 显示「搜索到 0 条结果。」，页面上却仍有 1 个 `article`（内容是刚录入来源的条目），于是 `expect(page.locator("article")).toHaveCount(0)` 10 秒内 23 次都读到 1。该 `article` 只能是页面级 `FeedBrowser` 渲染的（全仓只有它渲染 `<article>`；看板阅读流区块用 `<ul><li><button>`），而 `onSearch` 在同一次状态更新里同时写 `activeSearch`、`feed` 与提示语，所以「提示语说 0 条、列表还留着上一次的内容」在代码上无法解释——**这是一个未查清的观察，不排除应用存在搜索状态不一致**。没有改这条断言，也没有用重跑结案。

**2026-09-17 结论（Task 30，按证据更正上面这段）**：那个 `article` 确实是页面级 `FeedBrowser` 渲染的，但它是**重复 key 造成的孤儿节点**，不是搜索状态不一致。MutationObserver 记录（Task 30 walkthrough）显示：列表渲染 20 张卡 → 搜索提交时 React 从同一个 `div` 上移除 **19** 张、`feed` 长度标记为 0、空状态的两个 `<p>` 随后插入，剩下那张卡从未被 React 接管（同一条 Story 在 Feed 里有两张成员卡片，storyId 相同）。因此搜索状态与提示语始终一致；`toHaveCount(0)` 读到的是 React 管不到的残留节点。判据：现场页头没有「N 篇内容」（`feed.length === 0` 时才不渲染），且 `div[data-branch="empty"]`（临时探针）出现在 DOM 里。

**失败时的具体症状（拆分场景那一次）**：拆分**之前**已通过 API 轮询确认「标签与收藏都在该 Story 上」，拆分**之后**再读同一条 Story，两项都不见了。trace 里带时间戳的顺序是：归并 → 加标签 → 加收藏 → 轮询确认通过 → 拆分 → 再读为空。

**当前判断**：

- 失败点漂移 + 单跑不复现 + 只出现在多场景连跑时，符合「测试之间共用环境互相干扰」，而不是某个功能的确定性缺陷。
- **但机制未查清，且不能排除应用存在并发/顺序缺陷。** 「前面有、后面没有」在严格串行的读写序列下不可能发生，说明上述假设里有一个是错的（读打到了别的 Story、某次写入晚于读取才落库、或某个连接看到了提交前的视图）——三者都没有被排除。
- 环境事实：Playwright 配置为 1 worker 串行、整套共用一个 API/Worker/SQLite/数据根；该文件有 7 个场景，每个各自新建真实 RSS 来源并触发一次真实抓取，Worker 每 50ms 轮询。仓库在单元测试层已多次记录 Windows 下 SQLite 的 `migrate deploy` 超时与 EBUSY，属同一家族。
- 看板切片之后，页面每个阅读流区块各发一次取数请求（叠加页面级阅读流），单位时间并发读增加，**可能**加剧了抖动；未证实因果。

**建议的处理次序**：

1. **先诊断**：把 SQLite 的 WAL 与 `busy_timeout` 显式配置上，并把请求与提交的顺序记录下来（`PROJECT-STATUS.md` 的「尚未实现」里本就有「SQLite WAL/busy timeout 的显式配置与并发行为验收」，怀疑与它是同一根因）。
2. **再决定修哪一侧**：若结论是测试环境互相干扰，让每个场景用自己的数据根（最彻底、最慢）；若怀疑应用并发，就按 Bug 走。
3. **可选的低成本改善**：让看板所有阅读流区块共用一次取数而不是各发一次（产品侧也少一次冗余请求）。

**不要做的事**：

- 不要用「重跑就过」结案。同目录 `ingest.spec.ts:127` 的 390px 溢出断言已在 CI 三次失败、每次重跑即过（记录见 `.agents/tasks/governance/G06-redline-code/README.md` 与第 2 条），最后判定是断言本身太弱。这类结论要连断言一起改。
- 不要在没弄清机制前，把「断言改宽松」当成修复——那会把真实竞态一起藏起来。
