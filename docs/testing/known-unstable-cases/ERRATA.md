# 勘误：已知不稳定用例分册 0001

分册 [`0001-browser-intermittent.md`](0001-browser-intermittent.md) 是 2026-09-25 之前的历史记录，封口后只读；其正文里"仍未归因"的表述已被下列更新取代（当前状态以主文档 [`../known-unstable-cases.md`](../known-unstable-cases.md) 第 1 条与本文件的勘误 1–4 为准）。

## 勘误 1（2026-09-25）：正文第 3、7 行"仍未归因"的三点都已归因

分册第 3 行与第 7 行写着 `:103`、`:417` 与 `collection-plan-multi.spec.ts:63` 仍未归因。三点现已归因并修复：

- `:103`（证据关系反向视图）：**测试缺陷**。面板打开时本来源只录入 1/3 条，候选列表里只剩别的来源的条目；按位置挑中的条目属于别的来源，再按"来源名 + 标题"回找卡片会落到本来源同名的另一条 Story 上。修法：等本来源三条 fixture 卡片都出现，证据条目按来源身份挑。
- `:417`（用户组织场景，单次 5.1 分钟）：**产品缺陷**。列表的多个异步读取者之间没有顺序保证，先发起的读取晚落地会抹掉刚建的实体/Topic；扣住首屏 `/api/v1/entities?limit=50` 的响应可确定性复现"7 秒后该项从侧栏消失"。修法：列表写入闸门增加读取序号轴。
- `collection-plan-multi.spec.ts:63`（等「录入任务已排队」15 秒）：**测试缺陷**。该提示在坏来源下只存在 480–554ms，且失败提示可能先于它出现；轮询断言会随慢轮落空。修法：页面内记录提示语变化，断言"记录里出现过这段文字"。

## 勘误 2（2026-09-25）：正文第 3 行的 `media-policy` 归因

分册第 7 行把 `media-policy.spec.ts` 的来源健康行与本条的 `:103`／`:417` 并列为同类。该条已在主文档第 4 条单独更新：**当前代码上未复现**，已排除计划列表的陈旧读取这一机制，并修掉了它唯一已知的前置条件（读取风暴）；不声称已修。

## 勘误 3（2026-09-25）：正文第 28 行的 `ingest.spec.ts:119`

分册第 28 行把 `ingest.spec.ts` 的 `toBeFocused` 超时列为同族未查清项。它已归因：**测试缺陷**——该用例自己会归并并改标题，Feed 按更新时间重排，`.first()` 从被点的卡片移到另一张；焦点其实还给了被点的那个节点。修法：断言绑到被点击的节点本身。

## 勘误 4（2026-10-08）：证据出处从 `Phase-2-UNDO.md` 迁到本文件

`Phase-2-UNDO.md` 已于 2026-10-08 **封口**（停止维护，只读）。上面勘误 1–3 的结论原本以该文件的 P4-1 段落为出处，现补上该段落独有、而勘误 1–3 未覆盖的两项证据，使本文件成为自足出处：

- **先修掉的产品缺陷（读取风暴）**：`page.tsx` 每次渲染新建的 workspace context 让 `use-source-workspace` 的挂载 effect 每次渲染都重跑。实测**一个页面会话对 `/api/v1/collection-plans` 发 313 次、`/api/v1/connections` 发 314 次读取**（3 秒静置窗口里 629 次）。修法：context 用 `useMemo` 固化身份，六处调用共用。修后同一窗口 ≤ 8 次；确定性回归 `e2e/browser/list-state-race.spec.ts`（修前 629 次 / 修后 ≤ 8 次）。**边界**：它是真实缺陷与持续负载，但**不是**台账里「整轮明显变慢」的成因——修后同 33 例的整套用时约 164 秒，与修前 160–162 秒基本一致；历史那次 2.9 分钟的慢轮本身包含一次 120 秒超时，慢是超时的**结果**而非前置条件。
- **点 3 顺带修掉的两个产品缺陷**（删掉读取风暴后才暴露，此前被 300+ 次重读掩盖）：① 新建连接后来源表单的连接下拉不刷新（`ConnectionPanel` 增 `onConnectionsChanged`，页面重读计划/连接列表）；② `run.failed.v1` 只刷新 Feed 不刷新计划列表，「请在计划行内查看错误信息」指的那一行永远没有错误（SSE 处理里同时重读计划列表）。

**未做**：`media-policy` 的历史现场无法回放（没有 trace、代码已多次变更）；`:417` 那一次 5.1 分钟同样没有 trace，机制是确定性复现出来的、不是那次现场的逐帧回放。证据存档在原工作区 `.agent/tmp/p41/`（修前 5 轮日志与失败 trace、定向诊断、修后 3 轮日志）。
