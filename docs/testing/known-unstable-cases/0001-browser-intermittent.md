## 1. `e2e/browser/phase2-organization.spec.ts` 的间歇失败

**状态（2026-09-17 更新，含一次更正）**：`:539` FTS5 搜索用例已查明并修复，但**根因不是陈旧响应竞态**（早先的归因有误，下面第 32 行的观察结论已按证据更正）。真实根因是 Feed 卡片列表的 **React key 重复**：同一 Story 可以有多张成员卡片同时出现在 Feed 里（ADR-0022 决定 4/6「只标记、不折叠」），列表却用 `storyId` 当 key，React 只接管其中一张，另一张的 DOM 节点不再受它管理——列表被整体替换后它就留在原地成为「幽灵卡片」，而此时提示语与 React 状态都已经是 0 条。修复（`key` 改用条目身份 `entryId`）与**确定性**回归用例（同一 spec 修复前必挂、修复后 14.9 秒通过）见 Task [`30`](../../../.agents/tasks/30-feed-stale-response-race/README.md)。同一次排查顺带确认了另一个**真实竞态**（搜索之后才返回的陈旧刷新会覆盖搜索置空的列表），已同批修复并带独立回归用例，但它不是 `:539` 的成因。本条现在只覆盖**仍未归因的 `:103`（证据关系反向视图等待超时）、`:417`（用户组织场景耗时异常，单次 5.1 分钟）与 `collection-plan-multi.spec.ts:63`（2026-09-22 新观察：等「录入任务已排队」提示 15 秒超时）**。

**症状**：整个 spec 文件连跑时，某个用例失败；失败点会在用例之间**漂移**，单跑又通过。

**2026-09-23 补充（EXT-006 分支）**：`webhook-entry.spec.ts` 那次失败已查明**不是**本条的抖动，而是一个确定性布局缺陷——固定宽度侧栏（`lg` 300px／`xl` 330px）里的连接面板不收缩（`min-content` 实测 398px，授权范围写长 JSON 时 1015px），画到右侧计划列表上挡住按钮。修法是把 `min-w-0` 铺到那条 flex/grid 链上（提交 `3ce3322`）；修后两次整套运行都没再出现该失败。本条仍只覆盖 `:103` 与 `ingest.spec.ts` 的 `toBeFocused`——这两条在同一构建上单跑都通过、只在整套里出现，机制仍未查清，**不要用重跑结案**。

**2026-09-17 关于 `:539` 的补充观察（Task 26 期间）**：失败现场 `role=status` 显示「搜索到 0 条结果。」，页面上却仍有 1 个 `article`（内容是刚录入来源的条目），于是 `expect(page.locator("article")).toHaveCount(0)` 10 秒内 23 次都读到 1。该 `article` 只能是页面级 `FeedBrowser` 渲染的（全仓只有它渲染 `<article>`；看板阅读流区块用 `<ul><li><button>`），而 `onSearch` 在同一次状态更新里同时写 `activeSearch`、`feed` 与提示语，所以「提示语说 0 条、列表还留着上一次的内容」在代码上无法解释——**这是一个未查清的观察，不排除应用存在搜索状态不一致**。没有改这条断言，也没有用重跑结案。

**2026-09-17 结论（Task 30，按证据更正上面这段）**：那个 `article` 确实是页面级 `FeedBrowser` 渲染的，但它是**重复 key 造成的孤儿节点**，不是搜索状态不一致。MutationObserver 记录（Task 30 walkthrough）显示：列表渲染 20 张卡 → 搜索提交时 React 从同一个 `div` 上移除 **19** 张、`feed` 长度标记为 0、空状态的两个 `<p>` 随后插入，剩下那张卡从未被 React 接管（同一条 Story 在 Feed 里有两张成员卡片，storyId 相同）。因此搜索状态与提示语始终一致；`toHaveCount(0)` 读到的是 React 管不到的残留节点。判据：现场页头没有「N 篇内容」（`feed.length === 0` 时才不渲染），且 `div[data-branch="empty"]`（临时探针）出现在 DOM 里。

**失败时的具体症状（拆分场景那一次）**：拆分**之前**已通过 API 轮询确认「标签与收藏都在该 Story 上」，拆分**之后**再读同一条 Story，两项都不见了。trace 里带时间戳的顺序是：归并 → 加标签 → 加收藏 → 轮询确认通过 → 拆分 → 再读为空。

**当前判断**：

- 失败点漂移 + 单跑不复现 + 只出现在多场景连跑时，符合「测试之间共用环境互相干扰」，而不是某个功能的确定性缺陷。
- **但机制未查清，且不能排除应用存在并发/顺序缺陷。** 「前面有、后面没有」在严格串行的读写序列下不可能发生，说明上述假设里有一个是错的（读打到了别的 Story、某次写入晚于读取才落库、或某个连接看到了提交前的视图）——三者都没有被排除。
- 环境事实：Playwright 配置为 1 worker 串行、整套共用一个 API/Worker/SQLite/数据根；该文件有 7 个场景，每个各自新建真实 RSS 来源并触发一次真实抓取，Worker 每 50ms 轮询。仓库在单元测试层已多次记录 Windows 下 SQLite 的 `migrate deploy` 超时与 EBUSY，属同一家族。
- 看板切片之后，页面每个阅读流区块各发一次取数请求（叠加页面级阅读流），单位时间并发读增加，**可能**加剧了抖动；未证实因果。
- **2026-09-24 更正（Task 34 实测）**：上面「怀疑与 WAL/busy timeout 未显式配置同根因」这条**只对了一半**——WAL 确实没开（`journal_mode=delete`），但 `busy_timeout` 由 Prisma 引擎默认设为 **5000ms**，所以「显式配置 busy_timeout」在当前实现下是空操作。
- **2026-09-24 更正（Task 34 实测）**：Prisma 对 SQLite 的交互式事务**本来就发 `BEGIN IMMEDIATE`**（诊断日志实测到该语句）。因此「延迟事务先读后写、升级写锁失败时不走 busy handler」这个经典陷阱**在本仓库不适用**，不要再从那个方向查。
- **2026-09-24 结论（Task 34，负结果）**：SQLite 锁/慢操作**不是**这些失败的成因，台账原先「怀疑与 SQLite WAL/busy timeout 同根因」**不被证据支持**。8 轮整套里 4 轮失败，其中 **3 轮的慢操作总数为 0**（含一次 7.2 分钟、`locator.fill` 卡满 300 秒的卡死）；唯一有慢操作爆发的第 5 轮里，同轮**通过**的用例也有 19 条慢操作落在自己的区间内——慢操作既非充分也非必要条件。此前基于单轮（n=1）写下的「失败轮次伴随慢操作爆发」**不成立，在此撤回**。
- **2026-09-24 失败症状归类（Task 34）**：失败集中在 **DOM/前端层**——元素找不到（run 5、7）、元素 5 分钟内始终不可填充（run 4）、状态深比较不等（run 6）；失败点漂移、单跑通过的特征不变。这更像前端状态/渲染竞态或请求未落地，而不是数据库争用。
- 另有一个**独立成立但与上述失败无因果**的事实：两个并发写事务会让其中一个等满 `busy_timeout`（5 秒）后失败。它证明争用真实存在，仅此而已。

**建议的处理次序**：

1. **先诊断（数据库这条线已证伪，转向前端）**：Task 34 已交付一个默认关闭的 SQLite 诊断开关并据此**排除**了「SQLite 锁/慢操作同根因」这条候选路径（见上方 2026-09-24 结论）。台账原先写的「把 WAL 与 `busy_timeout` 显式配置上」经实测**不必做**——`busy_timeout` 已是 5000，WAL 与这些失败的关系已被证伪。**下一步**：Playwright 配置为 `trace: "retain-on-failure"`，4 次失败的 trace 已在 `test-results/`；逐份看 trace 回答「页面当时在等什么」（哪个请求没落地、哪个元素没渲染），再按结果决定是前端 Bug 还是测试环境隔离。
2. **再决定修哪一侧**：若结论是测试环境互相干扰，让每个场景用自己的数据根（最彻底、最慢）；若怀疑应用并发，就按 Bug 走。
3. **可选的低成本改善**：让看板所有阅读流区块共用一次取数而不是各发一次（产品侧也少一次冗余请求）。

**不要做的事**：

- 不要用「重跑就过」结案。同目录 `ingest.spec.ts:127` 的 390px 溢出断言已在 CI 三次失败、每次重跑即过（记录见 `.agents/tasks/governance/G06-redline-code/README.md` 与第 2 条），最后判定是断言本身太弱。这类结论要连断言一起改。
- 不要在没弄清机制前，把「断言改宽松」当成修复——那会把真实竞态一起藏起来。
