## Decisions and Deviations

### 1. 台账第 7 条的归因是错的，本次更正

第 7 条（2026-09-20 登记）写的是「CI runner 更慢时单个用例越过 **15 秒默认上限**」，建议「考虑给该文件显式 `testTimeout`」。实测环境事实推翻了这两点：

- `vitest.config.ts` 的全局 `testTimeout` 是 **60 秒**，配置里还带着注释：「Prisma/SQLite 用例单条 3~5s，与 vitest 默认 5s 余量过窄，并行时偶发假失败」。**15 秒不是默认值，是该文件自己覆盖出来的。**
- 该文件四处显式超时：`15_000`／`15_000`／`15_000`／`20_000`。
- 本机实测四条用例分别 **5712ms / 5213ms / 4426ms / 5402ms**，整文件 19.1~20.8 秒。

所以问题不是「全局预算太紧」，而是**这个文件把自己的预算调到了与全局设定和既定理由相矛盾的水平**，在慢 runner 或并发争用下必然越过。修法因此是**删掉覆盖**（不新增数字），而不是「再给一个显式值」。

### 2. 区分「派生 EBUSY」与「独立 EBUSY」

G15 两次全量失败里都有 `EBUSY`，但机制不同：

| 轮次 | 形态 | 性质 |
| --- | --- | --- |
| run #1 | parity 用例 `Test timed out in 15000ms`，**随后**清理撞 `EBUSY` | **派生**：用例被中断时库还开着，清理自然删不掉。本片的修复消掉它。 |
| run #2 | `story-human-protection.test.ts` 清理撞 `EBUSY`，**同一条用例无超时报错** | **独立**：用例跑完了、清理时文件仍被占用。本片不修，登记为第 8 条。 |

把两者混为一谈会得出「改了超时就都好了」的错误结论。
