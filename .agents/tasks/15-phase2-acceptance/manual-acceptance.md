## 这份脚本解决什么

Phase 2 的四条主流程（Topic / Entity / 用户组织 / 看板）到 2026-09-15 为止**只有自动化证据**：浏览器 E2E 证明代码路径能走通，不证明人能用得下去。本脚本把四条流程拆成可以照着点的步骤，由维护者实际走一遍并记录卡住的地方。

自动化测试与本脚本不能互相替代：自动化失败是回归，本脚本要回答的是"这个功能对不对、顺不顺手"，例如标签多了会不会难选、看板编辑会不会误删、Story 拆分后用户标记去哪了是否讲得清。

## 前置准备

1. 拉起本地开发环境（`bun run dev` 起 Web + API + Worker），浏览器打开 Web 首页。
2. 库里至少要有 **2 条 Story**，且最好来自 **2 个不同来源**——多来源 Story 是 Phase 2 的核心验收对象。若库是空的，先建一个真实 RSS 来源并手动跑一次采集。
3. 至少有 **1 个 Label**、**1 个 Entity**、**1 个 Topic** 是跨 Story 复用的，否则"筛选""相关内容""共享分类"这些点不出效果。
4. 找一张纸或直接在本文件末尾的记录表里记。**卡住、看不懂、点了没反应、文案说不清**都算发现，不必等到出错。

## 记录方式

每条流程记三样：能不能走通、哪一步卡住、**你觉得该怎样**。第三条最重要——你不需要写缺陷报告，只描述你的预期和实际看到的不一致即可。

## 流程 A：Topic

| #   | 操作                                                                   | 期望看到                            |
| --- | -------------------------------------------------------------------- | ------------------------------- |
| A1  | 打开一条 Story，在"创建 Topic 并加入本 Story"里填 `Topic 标题` + `关注目的`，点 `创建并加入`    | Story 出现在新 Topic 的成员里，角色是默认角色   |
| A2  | 打开另一条 Story，在"加入 Topic"区块选同一个 Topic + 一个角色（核心/进展/背景/分析/反方/教程），点 `加入` | 该 Story 成为同一 Topic 的成员，角色是你选的那个 |
| A3  | 点进 Topic 详情，把某个成员的角色改成另一个值                                           | 角色变更后列表立即更新；重新进入仍是新角色           |
| A4  | 对某个成员点 `移除`                                                          | 成员进入已移除状态，不再是当前成员               |
| A5  | 对刚移除的成员点 `恢复`                                                        | 成员恢复为当前成员                       |

**重点问自己**：六个角色名（核心/进展/背景/分析/反方/教程）你一眼能分清该选哪个吗？成员多了之后，你能看出谁是什么时候、因为什么被加进来的吗？"移除"和"恢复到原角色"是否让你放心，还是你不敢点？

## 流程 B：Entity

| #   | 操作                                                                        | 期望看到                              |
| --- | ------------------------------------------------------------------------- | --------------------------------- |
| B1  | 打开一条 Story，在"创建 Entity 并关联本 Story"里填名称 + 选类型（人物/组织/产品/项目/模型/地点），点 `创建并关联` | Entity 创建成功并出现在该 Story 的关联实体里     |
| B2  | 打开另一条 Story，在"关联已有 Entity"里选中刚建的 Entity，点 `关联`                            | 两条 Story 共享同一 Entity              |
| B3  | 打开该 Entity 详情，在"添加别名"里填另一个写法                                              | 别名出现在别名列表                         |
| B4  | 在"Entity 操作"区选一个关系目标 + 关系类型（创立/任职于/位于/产出/属于/相关），点 `添加关系`                  | Entity 之间出现该关系，方向与你理解的一致          |
| B5  | 在 Entity 详情"关联 Story"里对某条 Story 点 `解除关联`                                  | 该 Story 不再关联此 Entity，Story 侧也同步消失 |

**重点问自己**：六种 Entity 类型和六种关系类型的命名，你不用查文档就知道该选哪个吗？关系是**有方向的**（A→B 和 B→A 不同），界面有没有让你意识到这一点？同一个 Entity 的两种写法，你更希望系统提示"可能是同一个"，还是希望你手动加别名？

> 备注：Entity 目前**不能合并**（不能把"某公司"和"某某公司"合成一个）。这是本次已知缺口，不算缺陷，只记录你是否觉得需要。

## 流程 C：用户组织（标签 / 收藏 / 收藏夹 / 批注 / 已保存视图）

都在 Story 详情面板的"用户组织"区，另加 Feed 搜索区的"已保存视图"。

| #   | 操作                                                        | 期望看到                        |
| --- | --------------------------------------------------------- | --------------------------- |
| C1  | 点 `☆ 收藏`，再点 `★ 取消收藏`                                      | 状态正确切换                      |
| C2  | 在"选择标签…"选一个已有标签点 `添加`；再用 `新标签名称` + `创建并添加` 新建一个           | 两个标签都挂上；重复新建同名标签有明确反馈       |
| C3  | 点标签上的移除控件删掉一个                                             | 只删该 Story 上的这一条，不影响别的 Story |
| C4  | 勾选/取消某个收藏夹的复选框                                            | 收藏夹成员随之增减                   |
| C5  | 用 `新收藏夹名称` + `新建收藏夹` 建一个收藏夹                               | 新收藏夹出现并可用                   |
| C6  | 在批注框写正文点 `添加批注`；再对这条点 `编辑` → 改内容 → `保存`；最后点 `删除`          | 三步都符合预期；编辑态有明确的 `取消` 退出路径   |
| C7  | 在 Feed 搜索区设好筛选条件，填 `视图名称` 点 `保存当前条件`；然后**改掉筛选项**，再点该视图名套用 | 套用后筛选条件（含分类、Topic 多选）完整回填   |
| C8  | 点该视图的 `删除`                                                | 视图消失，但不影响任何 Story/Entry 数据  |

**重点问自己**：标签和收藏夹的区别你会不会混？新建标签/收藏夹的入口够不够顺手（是不是每次都要先关掉别的）？批注会不会让你担心"下次 Story 更新它就丢了"？

## 流程 D：看板

| #   | 操作                                             | 期望看到                                   |
| --- | ---------------------------------------------- | -------------------------------------- |
| D1  | 点顶部 `编辑看板` 进编辑模式，再点 `完成编辑` 退出                  | 两态切换清晰，非编辑态不该出现编辑控件                    |
| D2  | 编辑模式下加一个分区（`新分区标题` + `添加分区`）                   | 新分区出现在看板上                              |
| D3  | 用类型下拉（阅读流/热点/来源健康/Topic 列表/收藏夹）+ `添加区块` 各加一个   | 每类区块都能加出来；需要绑定的（阅读流绑保存视图、收藏夹绑收藏夹）能选到目标 |
| D4  | 对区块依次试 `上移`、`下移`、`隐藏`、`显示`、`复制`、`移到`（跨分区）、`删除` | 每次操作后看板立即正确更新；`删除` 只删区块                |
| D5  | 对分区试 `上移`、`下移`、`删除分区`                          | 同上                                     |
| D6  | 顶部 `切换看板` 下拉切换；编辑模式下用 `新看板名称` + `新建看板` 建第二个看板  | 多 Board 互不干扰，各自配置独立                    |
| D7  | 打开一条 Story 点 `固定到看板热点区`；再去看板热点区块点该条目的 `解除`     | 固定/解除都生效                               |

**重点问自己（这条最关键）**：**删除一个区块之后，你的收藏、标签、批注、Story 本身是不是都还在？** 这是 PRD Phase 2 的第三条验收标准，请专门验证一次并明确回答"还在"或"丢了"。另外：区块移动只有上移/下移没有拖拽，你在实际整理看板时会不会因此烦躁？改错一步能不能撤销（当前没有撤销）？

> 已知限制，不要当缺陷记录：多个"阅读流"区块目前**只有第一个**渲染真实内容，其余显示占位；本次收口的"看板 UI 缺口"正在修这一条与拖拽排序。

开发者总结：上述功能基本完整，但是都没有完整独立UI，许多功能堆积到Story的UI面板中，这导致功能分散+Story UI混乱，让用户不知所措。一个好的UI应该本身就包含优秀的引导 ，不要让用户到处探索。UI方面还有一个严重的问题：文案太过于专业化，让用户有所困惑。UI文案可以专业，但不能太专业，必须保证大部分正常用户能够一眼看懂。

## 已知限制（不要当缺陷报）

- 多个阅读流区块只有第一个渲染真实内容（本次收口正在修）；区块不能拖拽排序（正在修）。
- Entity 不能合并/去重；批注只能挂整条 Story/Entry/Topic，不能锚到正文某一句。
- 没有"未读"过滤；相关内容没有服务端排序、最多 5 条（属 Phase 4 推荐体系）。
- Story 拆分后，你的收藏、标签、收藏夹、批注、看板固定**全部留在旧的历史壳上**，且没有撤销入口——这是本次收口要做的"split 用户状态迁移"，在它落地前属已知限制。
- Docker/Compose、发布部署、真实公网长时定时抓取、非 Windows 平台 smoke、长时间故障恢复按 2026-09-07 划线保留为 Phase 1 后置债。
