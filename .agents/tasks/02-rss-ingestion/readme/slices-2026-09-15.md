### 切片：搜索文本按字面处理（2026-09-15，Bug 修复）

- **生命周期阶段**：已实现、门禁通过，待维护者验收合并（分支 `fix/t02-search-fts5`，worktree `.worktree/fix-search-fts5`，基线 `e25b853`）。
- **问题与证据**：`search` 把用户输入原样交给 SQLite FTS5 的 `entry_search MATCH ?`（`packages/storage-prisma/src/repository/search.ts`）。FTS5 的 `MATCH` 有自己的查询语言，`-` 是 NOT 运算符，于是 `绝不匹配-212c82` 变成畸形查询，SQLite 回 `fts5: syntax error near ""`，整个请求返回 500。`*`（前缀通配）、引号、括号属同一类；`OR`/`NEAR` 会被静默执行成用户没要求的布尔语义；带连字符的正常词（`state-of-the-art`）根本搜不到。发现路径：看板切片新增的浏览器用例用了一个带连字符的搜索词，trace 里出现 `500 GET /api/v1/search?text=…-212c82&limit=5`。
- **影响面**：用户可见缺陷，只影响文本搜索；带连字符的英文词与含括号/引号的查询在全仓搜索里同样受影响。
- **修法（维护者 2026-09-15 选定「全当字面文本」）**：输入按空白切成词，每段作为字面短语查询、内部引号双写转义，多词之间保持 AND（与修复前普通词的行为一致）；没有可搜索词（只有 `-`、`()`、`***` 之类）时退回「无文本条件」，不构造空查询。取舍代价明确记录：搜索框不再是 FTS5 查询接口，`OR`/`NEAR`/前缀通配从此不再是运算符——这与 PRD §8.2「关键词和组合过滤」和现有 UI（一个关键词输入框 + 结构化筛选项）一致。
- **受影响合同**：无公共合同、无 Prisma schema/migration 变化；只改 `search` 的文本条件构造与 FTS 路径的选取条件。
- **验证层级**：storage 行为测试（隔离库 + 真实 ingest 路径）→ 浏览器真实 HTTP 表面 → 全量门禁。
- **先红后绿**：修复前新增 `packages/storage-prisma/src/search-query.test.ts` 3/3 失败，报错即 SQLite 的 `fts5: syntax error near ""`；修复后 3/3 通过。
- **验证（2026-09-15，worktree 内实际运行）**：`bun run typecheck` 0；`bun run test` **89 文件 / 527 用例**全绿；`bun run build` 通过；浏览器产品 E2E **19/19**（含新增 `searches a term carrying FTS5 syntax characters without failing`：接口返回 200、UI 搜索路径正常渲染）；组件实验室 **13/13**；`bun run docs:check` 626 文件 `failures=[]`。
