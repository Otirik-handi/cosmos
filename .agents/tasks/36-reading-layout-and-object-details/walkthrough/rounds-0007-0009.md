## Round 7（2026-10-03）：分隔线两头改圆角

维护者指令：「两头改成圆角」。实施：`separator.tsx` 给横向线加 `rounded-full`
（完整圆角半径被浏览器钳到高度的一半，实测 0.5em＝8 px 高 → 两端各一个 4 px 半圆帽）。
**竖向线不加圆角**：它只有 1 px 宽，加与不加看不出差别，而把 0.5em 的规则套上去会变成色块
（Round 6 已挡掉同一个坑）。

实测（Round 7）：真实面板 8 处 `height 8px / width 250 / borderRadius 3.35544e+07px`（＝`rounded-full`），
间距与溢出不变、console 错误 0；实验室横向 `1440×8`、`848×7` 截图确认两端为半圆。
未运行：浏览器与实验室 Playwright 套件（dev server 冲突，同 Round 4-6）。

### Round 7 追加：粗细从 0.5em 改成 0.75em

维护者看过 0.5em 后指令「可以改成0.75em」。改 `globals.css` 的 `--divider-thickness`
与实验室 token 默认值；实测真实面板 8 处 `height 12px`（16 px 字号）、圆角不变、间距不变、溢出 0。
这是**第一次由维护者在看过实物之后定的取值**（0.5em 是看图定的），记为现行值。

## Round 8（2026-10-03）：修掉「两条相邻的分隔线」

维护者反馈：

> 回到阅读页版面，我发现右栏中有两个并列的分割组件

**这是真缺陷，而且我在同一轮里犯了两次同一个错**：Round 5 把线放在「每个区块的尾部」，
于是只要两个区块相邻（`isShell` 时「已拆分」与「迁移用户状态」同时渲染），中间就会出现两条线；
同时 `history-shell.tsx` 与 `user-state-migration.tsx` 各自又**自带一条开头的线**，
两个组件相邻渲染时同样叠成两条。实测证据：三条线里

```text
isShell 时右栏的原始结构：[已拆分] 线 线 [迁移用户状态] 线 [编辑与关联]
```

### 修法：线的位置规则改成「只在相邻兄弟之间」

| 位置 | 修法 |
| --- | --- |
| `story-edit-panel.tsx` | 尾部线全部撤掉；改为「已拆分 → 线 → 迁移 → 线 → 编辑与关联」，每条线都夹在两个区块之间 |
| `history-shell.tsx` / `user-state-migration.tsx` | 删掉各自开头的线，容器从 `gap-2` 收到 `gap-1`（父级已经在区块之间给线，子组件不重复声明边界） |
| `link-entity.tsx` | 「关联实体」区块可能整块不渲染，原写法会留下孤儿线；改成「线 + 关联 Entity 区块」绑在同一条件里 |

`organization-editor.tsx` 与 `story-actions.tsx` 的三段结构本来就是「线夹在中间」，未受影响。

### 验证（Round 8）

```text
bunx tsc --noEmit -p apps/web/tsconfig.json   -> exit 0
bun run lint:web                              -> 0 error / 18 warning（回到基线；撤线后有 2 个未使用导入，已清）
.agent/tmp/t36-panel-children-probe.ts        -> 三个场景逐个列直接子元素：
    default     相邻双线=无（8 条线，均在区块之间）
    splittable  相邻双线=无
    split-shell 相邻双线=无：[已拆分] / 线 h=11 / [迁移用户状态] / 线 h=11 / [编辑与关联]
.agent/tmp/t36-separator-probe.ts             -> 真实普通故事仍 8 条、宽 250、高 12px、溢出 0、console 错误 0
```

**未运行**：浏览器与实验室 Playwright 套件（dev server 冲突，同前几轮）；拆分壳的真实数据页面
本轮用实验室 `split-shell` 夹具核对（真实库里没有拆分壳 Story）。

### 偏差（Round 8）

- **真实数据里没有拆分壳 Story**，所以「两个并列分割线」这一形态只能在实验室 `split-shell` 夹具上验证。
  维护者看到的是哪一个 Story 未确认；**如果他是从别的路径看到的（例如某个数据形态下的第三个相邻区块），
  这个修法可能没覆盖**——Round 8 的核对只覆盖 `isShell` 这一种组合。

## Round 9（2026-10-03）：右栏按类别重排为 C→B→A→D

维护者反馈「右栏有点杂乱」，并判定**是结构性问题导致的观感差**，要求先分类。Agent 给出按
「改的是哪一层数据」的 A/B/C/D 四类，维护者裁定**按使用频率排**、顺序为 **C→B→A→D**、
每类之间用分隔组件分割；追问后裁定：壳专属区块算 B 段、收藏移进 C 段。

### 分类与落位

| 段 | 名称 | 内容 | 判据 |
| --- | --- | --- | --- |
| C | 我的标记 | 收藏、固定到看板、标签、收藏夹、批注 | 只写「用户 × Story」，不改内容 |
| B | 家族与关系 | 归并、拆分；壳上另加已拆分、迁移用户状态 | 改多条 Story 的拓扑 |
| A | 内容与表示 | 标题/类型/subtype、时间范围、关键事实、保存修改 | 改当前 Revision（ADR-0028 保护） |
| D | 对象关联 | 关联 Entity、加入 Topic | 改关系表 |

重排前四类被切成六段，同类的聚不到一起：C 类分散在标题行与「用户组织」两处（收藏在标题行、
其余四个在中下），B 类分散在三处（壳上两处 + 归并藏在「改表示」内部 + 拆分），
而「用户组织」这个容器**同时装着 C 的四个与 D 的两个**——两类不同的东西共用一个容器。

### 实施（按段落划分组件，状态随段落走）

| 文件 | 改动 |
| --- | --- |
| `story-edit-panel.tsx` | 标题行只留展开/收起；按 C→B→A→D 组合四段，段间各一条分隔线 |
| `story-edit/marking-editor.tsx`（新） | C 段的写入层：把面板的 busy/错误漏斗套在六个标记写入上，另持「收藏进行中」 |
| `story-panel/story-marking.tsx`（新，取代 `story-panel/organization.tsx`） | C 段的表单与草稿：标签选择、收藏夹勾选、批注编辑中/新建。**草稿归本组件持有**——提到面板再传进来就是把状态留在原地只挪渲染位置 |
| `story-edit/entities-editor.tsx`（新） | D 段：关联 Entity、加入 Topic，各自持有自己的选择草稿 |
| `story-edit/organization-editor.tsx`（删除） | 它同时装着标记与关联两类状态，无法按段重排 |
| `story-panel/story-actions.tsx` | 撤掉内部两处线（见 Round 10）；`grid gap-4` → `flex flex-col gap-5` |
| `story-panel/revision-assets.tsx` | 撤掉自带的线 |
| `copy/areas/reading.ts` + `copy/inline-copy-baseline.json` | 新文件的 30 处文案迁进 `copy/`（`storyEdit.marking.*`），基线里两条已删文件的条目移除 |

**A 段与 B 段的草稿仍留在面板**：`0005-web-client.md` 写着「五份草稿的未保存判定在
`StoryEditPanel` 内」，把「改表示」的草稿抽走要同时改那条合同与 `story-representation` /
`story-live-refresh` 两套门禁，属于另一个合同决定，不在本轮。

### 门禁的连锁影响（本轮实测）

```text
apps/web/src/copy 门禁            -> 首跑失败：新文件 30 处内联文案 + 基线里两条已删条目
                                     （门禁按设计工作：新文件不允许带内联中文）
apps/web/src/component-lab 门禁   -> 通过（公共模块集合不变：新增 story-marking 与删除 organization 相抵）
```

### 验证（Round 9）

```text
bunx tsc --noEmit -p apps/web/tsconfig.json                      -> exit 0
bun run lint:web                                                 -> 0 error / 18 warning（回基线）
bunx vitest run apps/web/src/copy apps/web/src/component-lab      -> 32 passed

bun run test:browser:component-lab                                -> 21 passed（16.2s）
真实页面实测（.agent/tmp/t36-cbad-probe.ts）                       -> 见下
```

**真实页面实测**：标题行只剩「收起」；DOM 顺序为
`[编辑与关联] → 线 → [我的标记] → 线 → [Story 操作(改表示/归并)] → 线 → [关联 Entity] → 线 → [加入 Topic]`；
全页收藏按钮仍是 **1 个**（唯一入口不变）；无横向溢出；console 错误 0。

**实验室实测**（`.agent/tmp/t36-lab-collapse-probe.ts`）：展开时面板内 4 条线、收起后 **1 条**
（标题行与折叠提示之间那条，折叠提示也是「编辑与关联」的内容）；`我的标记` 段随收起消失。

### 被改掉的既有断言（Round 9/10）

| 断言 | 原样 | 改成 | 理由 |
| --- | --- | --- | --- |
| `component-lab/story-edit-panel.spec.ts` 「收起后收藏仍可见」 | `toBeVisible` | 收起时 `toHaveCount(0)`，展开后 `toBeVisible` | 收藏 Round 4 在标题行、Round 9 移进 C 段；C 段收起时不渲染，旧断言已过时 |
| 同文件「先点展开」两处 | 无条件 `click("展开")` | 去掉（默认展开）或不依赖初始态 | 默认展开后无条件点会把面板关掉 |
| 同文件新增 | — | 收起时面板内线数 = 1、展开时 = 4 | 把「线跟着区块走」变成可断言的合同 |

**一次自己造成的假红**：第一版断言写成「收起后面板内线数 = 0」，实测是 1 才明白
**标题行与折叠提示之间那条线在收起时也应该在**——折叠提示是「编辑与关联」的内容。
教训与 Round 2 那条同源：**断言的期望值要先量，再写**。
