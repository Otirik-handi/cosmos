## Round 13（2026-10-03）：改表示的三个字段各占一行

维护者给了一张截图，指出「改表示」里标题/类型/subtype 挤在一行、且**在行内折行**（标签与控件被拆开），
要求各表单独占一行。

**根因是 Round 9 加的一处 `max-w-xs`**：那一行原本是「标签 + 控件 + 标签 + 控件」的 `flex-wrap`，
右栏只有视口的 1/4 宽；标题输入框加上 320 px 上限后总宽超出，于是「类型」被折到第二行、
subtype 又自己掉一行。**逐字段一行、标签与控件同排**，是这个宽度下唯一稳定的形态。

实施：`story-actions.tsx` 把那一行拆成三个 `flex items-center gap-2`，标签加 `shrink-0`。

实测（1280 / 1440 两档）：三行 `rowTop` 分别 694 / 742 / 788，**每行一个字段**；
标签与控件顶部差 0（同行）、标签不折行；横向溢出 0、console 错误 0。

## Round 14（2026-10-03）：给 toast 序号，并修掉一个渲染期写 ref 的违规

Round 12 为了让测试稳定取到「最新一条回执」，给每条 toast 挂了自增序号。第一版在 `ToastHost`
**渲染期**写 `useRef` 分配序号，`react-hooks/refs` 直接报错
（`This value cannot be modified`）——渲染必须是纯的。

改成**提交时分配、渲染时只读**：`toastSequence` 模块级自增，序号写进回执的 `data`，
宿主从 `toast.data.seq` 读出挂成 `data-toast-seq`。实测「按序号取最新一条」在
`source-lifecycle-and-search-filters` 与 `feed-search-race` 上通过（这两条正是先前 `.last()` 取错的那两条）。

**教训与 Round 12 的 `noticeVariant` 同源**：这个仓库开了 React Compiler 的 lint，
「渲染期有没有副作用」和「上下文/引用对象能不能改」都是硬门禁——**先想清楚数据在哪一刻产生，
再决定放 ref、参数还是 state**，比事后修 lint 便宜得多。

### Round 17 追加：间隔从 16 px 加到 2.5em（40 px）

维护者看过一轮后指令：「间隔还是太小了，设置成2.5em试试」。

- **改动**：两个路由组 layout 的 `pt-4` → **`pt-[2.5em]`**。该层级字号 16 px（继承自 body，
  实测 `shellFontSize: 16px`），所以 **2.5em = 40 px**。用 em 而不是 px 与 V4 的形状/密度 token 同口径。
- **实测**：首页与信息库的侧栏、主内容顶边从 64 → **104**（间隔 40）；阅读页 `main` 的 padding-box
  顶仍是 64（`pt` 体现在子元素上），其子内容间隔同为 40。顶栏本身仍 64 px、内容垂直居中偏移 0。
- **一处探测脚本的自我纠正**：第一版量「间隔」时读的是**带 `pt` 的容器本身**（padding-box 顶 = 64，
  所以量出 0），看着像改动没生效。改成量真实子元素（`aside` / `main`）才是用户看到的间隔。
  教训：**量间距要量真正相邻的两个元素，不要量容器自身。**

## Round 18（2026-10-03）：左侧导航等比放大 1.5 倍

维护者指令：「左侧导航栏所有内容等比放大1.5倍」。

### 为什么不是「把 font-size 调大 1.5 倍」

侧栏的尺寸全是硬编码 px（`w-[196px]`、`h-7`、`text-[13px]`、`size-3.5`、`gap-4`…），
而 **Tailwind 的 rem 值按根字号算**——根字号 16 px 是 V4 给「界面密度 11–14 px」定的，把它调成
24 px 会让**全站**控件一起变大，不只是侧栏。`transform: scale(1.5)` 也不合适：它会把焦点环与
阴影一起拉伸发虚，且不改变布局占位。

**做法**：引入第 3 层 token **`--nav-scale: 1.5`**，侧栏每个尺寸写成
`calc(<原值> * var(--nav-scale))`。一个标量乘全部尺寸，才是真正「等比」，以后要调也只动这一处。

### 改动

| 文件 | 改动 |
| --- | --- |
| `app/globals.css` | 新增 `--nav-scale: 1.5`（第 3 层，含「为什么不用根字号/transform」的理由） |
| `components/shell/side-nav.tsx` | 宽度、nav 内边距与组间距、组标题字号与内边距、导航项行高/间距/字号/内边距、图标尺寸全部乘 `--nav-scale` |
| `(shell)/layout.tsx` | **整组限宽联动**：`max-w-[1120px]` → `max-w-[calc(196px*var(--nav-scale)+900px)]` |
| `e2e/browser/layout-and-budget.spec.ts` | `SIDEBAR_WIDTH_PX` 196 → **294**；`SHELL_MAX_WIDTH_PX` 1120 → **1218**（两个都是精确相等/和测断言） |

### 一处必须同时改的联动（否则直接踩门禁）

限宽不跟着放大时：**294 + 20 + 880 = 1218 > 1120**，`max-w` 会把主内容挤到 **806 px**，
直接违反「内容限宽 880」的门禁——整组限宽不是独立的数字，它由「侧栏 + 间距 + 内容」求和而来。
主内容区**保持 880 px**：行宽不随侧栏放大而变宽（与决策 6「行宽是阅读舒适度约束」同一口径）。

## Round 19（2026-10-03）：左侧导航跟随滚动

维护者指令：「左侧导航栏改成能够跟随滚动」。

### 改动前的实测

```text
侧栏自然高 502 px（--nav-scale 1.5、8 个导航项）
首页/信息库可滚动（文档高 2989 / 4438，视口 800）；滚动 400 px 后侧栏 top 由 104 → -296（跟着滚走）
/organize 不可滚动（文档高 = 视口高）
```

### 改法

`side-nav.tsx` 的 `<aside>` 加 **`sticky top-[calc(4rem+2.5em)]`**（`self-start` 保留）。

- **top 取 `4rem + 2.5em` = 64 + 40 = 104 px**：正是侧栏未滚动时的位置（顶栏高 + 顶栏下方间隔），
  所以贴上后不会发生位置跳变。两者都跟随各自的 token（顶栏高与 `pt-[2.5em]`），改一个不会让 sticky 错位。
- **用 `sticky` 而不是 `fixed`**：sticky 仍留在文档流里，窄窗口下「主内容被 flex 压缩」的算法不变，
  也不需要给主内容补一个等宽占位；`fixed` 会让侧栏脱离流、必须手工补偿宽度。
- 侧栏高度仍由内容撑开（ADR-0029 决策 2 的已知代价）：导航项多到超过视口高度时底部会被裁，
  该情况已登记在 ADR 的 Revisit Gate 第 1 条。
