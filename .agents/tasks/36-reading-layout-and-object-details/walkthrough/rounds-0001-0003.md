## Round 1（2026-10-02）：建 Task、定版面、切片 A

### 本轮切片与仍然有效的假设

**切片 A（Story 阅读页两栏版面 + 拆 `StoryEditSurface`）**，本轮唯一在做的事。

假设（若被推翻要回来改这一节）：

1. 阅读页隐藏侧栏是 ADR-0029 决策 2 的唯一例外，因此外壳「侧栏 + 内容整体限宽 1120 px」不约束本页。
2. V4 的「正文列 ≤34em」是**行宽合同**，与栏宽解耦：栏宽按 3:2 推、正文列独立限 34em。
3. 左栏的判据是「它是不是这条内容本身」，不是「有没有写入控件」。因此成员行上的转载标记表单
   与证据来源的添加表单留在左栏——`phase2-entry-relation.spec.ts` 与 `phase2-organization.spec.ts`
   依赖「成员行/证据不用展开编辑面就在页面上」，改成纯只读会让这些断言失效。
4. 「内联文案只减不增」门禁不允许新文件带内联中文，所以拆分成两个新文件**必须**同时把
   `story-edit-surface.tsx` 的 13 处文案迁进 `copy/`。这不是扩大范围，是拆分的必要条件。

### 版面决定（维护者 2026-10-02 直接指令，非 Agent 设计）

```text
左栏 内容 ≈544px（34em）  │  右栏 操作编辑 ≈363px（左栏 × 2/3）
列间距 24px，内容总宽 ≈931px 居中
```

| 项 | 取值 | 来源 |
| --- | --- | --- |
| 两栏比例 | 3:2 | 维护者原话「宽度之比为3比2」 |
| 左栏宽 | 34em | V4 行宽合同；**未改合同** |
| 右栏宽 | 左栏 × 2/3 | 由 3:2 推出 |
| 内容总宽 | ≈931 px 居中、两侧留白 | 维护者「不要完全占满导航栏下方」 |
| 三档断点 | 均 3:2，不堆叠 | 维护者裁定 |
| 右栏滚动 | 跟着页面滚，不吸附 | 维护者裁定 |
| 媒体位置 | 左栏，正文之后 | 维护者裁定 |

**实现方式**：宽度全部用 `em` 而不是 `px`——正文列 34em、右栏由 `grid-cols-[3fr_2fr]` 推出、
列间距 1.5em、整组 `max-w-[58.25em]`。这样三档断点不需要各自的规则：窄窗口下两栏与间距
一起按比例收窄，3:2 与 34em 两条约束在整档宽度内同时成立。

**「操作面板太靠下」的解法是换轴**：两栏从同一高度开始，读标题时右栏编辑入口已在同一屏。
不引入 sticky（维护者选择「跟着滚」）。

### 顺手修四条

1. **`live-provider` context value 加 `useMemo`**：`streamState` 每次连接状态变化都换新对象，
   不 memo 会让只订阅 topic 的页面跟着重渲染。
2. **归并选择器的可达性**：Combobox 自带键盘上下选择与 `aria-label`；外面用
   `role="group"` + `aria-labelledby` 指到「并入本条的内容」那行文字，两者分工不互相顶掉。
3. **SSE 门禁补唯一例外路由**：新增 `阅读页这个唯一例外路由不会另开第二条连接`。
4. **「编辑中不被覆盖」补其余四份草稿**：新增 `keeps every representation draft when an external
   change arrives mid-edit`，同时填标题/类型/时间范围/关键事实，外部改表示后逐字段断言草稿没动。

**排查记录（值得留）**：这条 SSE 断言第一版用 `openStory()`（内部 `page.goto`）导航，结果
「连接从 1 变 2」——看着像真实缺陷。诊断（抓每条 `/api/v1/events` 的时序与 resourceType）证明
两次请求都来自主 frame 且新的整页加载开了新连接：**`page.goto` 是整页重载，重载后当然有一条新连接**。
改成应用内点卡片导航、基线取 `goto("/library")` 之后的条数、断言衡量增量，才是这条合同的原意。
**教训：用 `page.goto` 测「切页不重建外壳」类合同会测成浏览器行为。**

另一处：时间范围输入框的 `getByLabel("开始时间的准确时刻")` 实测 `count=0`，
而 `input[aria-label="开始的准确时刻"]` 命中 1——Base UI 的 `Input` 自生成 id 并据此命名，
`getByLabel` 对它解析不到。测试改用属性选择器，**没有改产品组件**。

### 归并选择器的三个问题（Round 2 修，值得留）

切片 B 落地后完整 `test:browser` 出现 **3 条失败**，其中 `phase2-entry-relation` / `ingest` /
`phase2-organization` 都走归并。逐条查明后是**两个真问题 + 一个测试写法问题**：

1. **用例还在填已删除的粘贴框**：`e2e/support/story-flow.ts` 的 `mergeStoryInto` 与
   `phase2-entry-relation.spec.ts` 都在 `getByLabel("并入本 Story 的 Story ID")`，
   入口已换成选择器。改为按**目标标题**在选择器里选（先读目标的真实标题）。
2. **`getByRole` 的 `name` 默认精确匹配**：选项的可访问名是完整标题，传搜索片段进去
   一条都点不到。用正则做包含匹配。
3. **客户端二次过滤把候选全滤掉**（这条是产品缺陷，不是测试问题）：Base UI 的 Combobox
   会在服务端返回的候选上**再按输入串筛一遍**，而输入串是搜索词、选项标题是完整标题，
   两者不等长时结果为空。实测：打开时 2 条候选，一敲字变 0 条。
   修法是 `filter={null}`（`AriaCombobox.js:160` 把它解释为「恒真」，正是为外部过滤准备的）。

**测试侧最终策略**：不依赖搜索——先直接用完整标题在初始候选（打开就有最近 20 条）里选，
5 秒选不到再用标题前 6 个字搜索兜底。理由是服务端搜索按空白拆词、每段当字面短语，
拿标题片段去搜可能一条都命中不到（实测「Message with」对不上「Message without a web URL」），
而那属于搜索语义，不是这条归并合同要验的东西。

## Round 3（2026-10-03）：阅读页版面放宽到 80vw + 3:1

### 本轮切片与仍然有效的假设

**切片 A 重做（只改版面取值与随之而来的门禁/文档，不动结构与行为）**，本轮唯一在做的事。

维护者看完 Round 1 的版面后裁定（原话）：

> 我发现阅读页版面中，内容总宽还是太窄了。将内容总宽调整为屏幕大小的80%，居中。左右两栏宽度比3比1。

Agent 追问一项后维护者裁定：**正文跟着左栏自然撑满，不再限 34em**。三档断点都用 80% + 3:1，
1024 px 以下仍按 ADR-0029 决策 6 只显示「窗口过窄」提示。原话已按固定顺序追加到
`docs/requirements/0001-original-requirements.md` 的 2026-10-03 一节。

### 取值（取代 Round 1 的 3:2 + 整组限宽）

| 项 | Round 1 | **Round 3（现行）** |
| --- | --- | --- |
| 整组宽 | `58.25em` ≈ 931 px | **视口 80%**（`w-[80vw]`） |
| 两栏比 | `3fr_2fr`（3:2） | **`3fr_1fr`（3:1）** |
| 列间距 | `gap-[1.5em]` | `gap-6`（24 px） |
| 正文列 | `max-w-[34em]`（≈544 px 上限） | **`w-full`，跟着左栏撑满** |

**实现方式**：整组 `mx-auto w-[80vw]`，两栏 `min-[1024px]:grid-cols-[3fr_1fr]`，列间距 `gap-6`（24 px）。
比例由 fr 分配、中间只有一个固定 24 px gap，所以实测比例正好 **3.00**：1280 档整组 1024 px、
两栏 750/250；1920 档整组 1536、两栏 1134/378。门禁仍取 2.9–3.2 而不是「= 3.0」，留出亚像素与
滚动条占位的余地。

### 被改掉的既有合同与断言（逐条理由）

| 项 | 原样 | 改成 | 理由 |
| --- | --- | --- | --- |

| `story-reading.spec.ts` 比例 | 1.35–1.65（3:2） | 2.9–3.2（3:1） | 比例本身是本次引入的合同，必须跟着改；区间留出 fr+gap 的固有偏差 |
